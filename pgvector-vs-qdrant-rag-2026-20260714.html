Executive Summary

Bottom Line

The one-question decision rule
Is your vector store the primary database or a satellite service? pgvector wins when you already run Postgres and want hybrid relational+vector queries in one system — simpler ops, native SQL joins, and built-in GDPR compliance. Qdrant wins when vector search is the primary workload and you need purpose-built filtering performance with lower single-query latency.

The 11.4× throughput gap in benchmarks favors pgvectorscale at high concurrency — but that benchmark was published by Timescale, who builds pgvectorscale. Qdrant holds a verified 2.75× single-query latency advantage at 1M vectors. Neither system has a decisive algorithmic edge: filtered ANN (approximate nearest-neighbor) search is an active 2025–2026 research frontier and both are still catching up to state-of-the-art implementations.

§1 · Metadata Filtering

Architecture Determines Performance

How Each System Works

QDRANT

Applies payload filters inside the HNSW graph traversal — single pass. Payload fields are indexed; filter runs during graph navigation, not after. Overhead: 1–2ms. Total filtered p50 at 500K vectors: ~6ms. ● HIGH

PGVECTOR

Uses SQL WHERE clauses — filter runs either before (risk: miss vectors) or after retrieval (risk: over-retrieve). HNSW indexes are not payload-aware. Filtered p50 at 500K vectors: 25–29ms. ● HIGH

⚠ pgvector 0.8.0 Iterative Scans (2025)
Progressively expands search radius when filters exclude too many candidates — directly addressing recall degradation under selective filters. Performance improvement at scale not yet independently benchmarked. ● MEDIUM

2026 Research Frontier

Filtered ANN search is an active academic frontier — both systems are behind optimal:

  • ArXiv 2402.00943 (Engels et al., 2024): Window Filter approach achieves 75× speedup over baseline filtered ANN on range queries.
  • ArXiv 2607.00727 (Tao et al., 2026): Graph Range Filters achieve 70.3% throughput improvement at 98.5% recall — directly targets the HNSW+filter bottleneck pgvector hits today.
  • GitHub pgvector issue #259: HNSW+filtering flagged as "challenging to implement correctly." ● MEDIUM
Verdict: Qdrant wins — selective filters pgvector wins — relational joins

If your RAG queries filter by user_id, tenant_id, or date ranges on large collections, Qdrant's architecture is meaningfully better. If you join across user tables, permissions, or content graphs, pgvector's SQL is the lower-friction path.

§2 · Scale Limits

Throughput vs Latency: Two Different Questions

⚠ Vendor Bias Alert — Timescale Benchmark
The 471 QPS vs 41 QPS benchmark was published by Timescale, the company that builds pgvectorscale. The raw numbers are independently reproduced by 4 sources and the methodology appears sound, but the workload selection may favor pgvectorscale's strengths. Interpret the 11.4× framing with caution.

Reconciliation: these are orthogonal metrics
pgvectorscale's 11.4× QPS advantage emerges at 50M vectors under sustained concurrent load — DiskANN-based SBQ (Statistical Binary Quantization) index is optimized for throughput. Qdrant's 2.75× p50 advantage is measured at 1M vectors on single queries. Qdrant delivers faster individual queries; pgvectorscale handles more concurrent requests.

Scale Ceiling

  • pgvector (standard HNSW): Reliable to ~50M vectors single-node before RAM and latency bottleneck. Confirmed by multiple practitioners. ● HIGH
  • pgvectorscale: Extends viability via SBQ + DiskANN. Ceiling ~500M cited ● UNVERIFIED — source 403; public benchmarks peak at 100M.
  • Qdrant: Handles 10s–100s of millions single-node; distributed mode via Kubernetes operator for horizontal scaling. No documented hard ceiling. ● MEDIUM

At disk scale: ArXiv 2602.21514 shows I/O accounts for 70–90% of ANN latency in disk-resident deployments — disk architecture matters more than the index algorithm at very large scale. ● HIGH

Verdict: pgvectorscale — concurrent throughput ⚠️ vendor bias Qdrant — single-query latency
§3 · Operational Overhead

One Database vs One More Service

Setup Complexity

PGVECTOR — existing Postgres
CREATE EXTENSION vector;

Minutes if Postgres already runs. Requires tuning: maintenance_work_mem (16 GB for large builds), parallel index workers (Postgres 16+), connection pooling (PgBouncer).

QDRANT — cold start
docker run -p 6333:6333 qdrant/qdrant

Single binary, production-ready in minutes. Docker Compose, K8s StatefulSet, Qdrant Cloud managed. No shared-memory tuning. ✅

Ongoing Maintenance Pain Points

PGVECTOR CHALLENGES
  • Index timing: Can't create index on empty table; too late = memory spike. v0.8.0 Iterative Scan helps. ● UNVERIFIED primary source
  • Index builds: 10M rows × 1536-dim = hours single-threaded; parallel builds (Postgres 16+) help but need CPU budget.
  • Vacuum: Autovacuum required; GDPR mass deletes trigger bloat if misconfigured.
  • Postgres expertise: WAL management, replication lag, connection pooling — prerequisite.
QDRANT CHALLENGES
  • Separate service: Independent deployment, monitoring (Prometheus available), restart policies, backup strategy.
  • Snapshot management: Not Postgres-compatible; separate backup tooling.
  • Multi-node ops: Distributed mode adds raft-based consensus and rebalancing complexity.
  • Security: Separate auth layer (API keys or mTLS) vs PostgreSQL RBAC.
